# 改造方案比较模板

版本：1.0；编制日期：2026-10-03。用途：在同一老旧小区现状下，整理两套改造措施、投入、受益范围和维护安排，明确下一步需要调查什么。

这是一份可填用的设计模板。配套 [JSON](../data/templates/retrofit-plan-template.json) 保存完整方案，[CSV](../data/templates/retrofit-plan-items.csv) 便于填写措施明细；目前没有新增方案保存 API、自动比较服务或界面导入功能，不能直接作为 `ProjectInput` 提交。后续接入应复用既有来源、文档解析和版本能力。当前产品依据见[产品与验证方案第 5 节](老旧小区改造_产品与验证方案.md#5-调整开发方案与静态测算)。

## 1. 怎样开始填写

1. 为方案 A 和 B 各复制一份 JSON。填写相同的 `project_id`、研究对象、`baseline_snapshot_ref`、快照哈希、研判时点、开发模式和测算期间；同一现状中的楼栋编号不要重新生成。
2. 为各方案填写 `plan_id`、`plan_version`；修订原方案时填写 `parent_version`。`template_version` 是表单版本，不能替代方案版本或业务规则版本。
3. 先列出拟研究的全部措施，再填写 `included`：`true` 表示纳入当前方案，`false` 表示明确不纳入，`null` 表示尚未决定。同一措施在方案之间沿用 `measure_id`，位置、数量或受益范围变化单独记录。
4. 填写工程量、报价、资金和维护资料。JSON 中未知数值用 `null`，CSV 空单元格对应未知；明确核实的零值才填 `0`。不要为获得总价，把缺失费用填零。
5. 关联原文、记录待核任务，然后填写比较结果。未完成计算的 `calculations` 保持 `not_computed`；空白比较字段表示还没有比较，不能解释为“没有变化”。

模板中的 `MEASURE-001` 等仅是空行标识，不代表真实设施或资料。需要多行时复制并分配稳定的 ID；没有这类项目时删除占位行，不能保留空行又宣布金额已完整。`object_refs` 使用已有 `project:…`、地图/楼栋对象引用；仅能定位到小区时明确写小区范围，不由模型补写某栋编号。开发模式预填 `comprehensive_renovation`，企业角色仍需写明施工承接、受托策划或其他具体角色。

## 2. 方案口径与措施明细

| 填写项 | 字段及要求 |
|---|---|
| 对象与空间范围 | `project_id`、`object_refs`、`scope_description`；区分项目、小区、楼栋、设施和周边片区 |
| 现状快照 | `baseline_snapshot_ref`、`baseline_snapshot_hash`；引用同一已保存的现状输入或工件，不仅填写相同日期 |
| 方案版本 | `plan_id`、`plan_version`、`parent_version`、编制人和时间；每次金额或范围修改形成新版本 |
| 统一测算口径 | `as_of`、`budget_period`、`price_basis_date`、币种和金额单位；默认金额用人民币元，不与现有万元输入直接混用 |
| 规则及角色 | `development_mode`、`enterprise_role`、`rule_version`；缺少专业复核时留空，不自行填写法律门槛 |
| 措施分类 | `category=basic/improvement/enhancement`，对应基础、完善、提升；具体归类应按项目适用文件复核，未知填空 |
| 纳入情况 | `included` 三态、`inclusion_reason`；不纳入、未决定、纳入但缺报价必须分别表达 |
| 工程范围 | `object_refs`、`location_description`、`quantity`、`quantity_unit`、`construction_phase`；对同一工程量只能计一次 |
| 单价与价税 | `unit_price`、`price_per_unit`、`tax_basis`、`tax_rate_percent`、`quoted_at`、`price_valid_until`；`price_per_unit` 是价格对应的工程量单位 |
| 受益范围 | `beneficiary_group_refs`、范围描述、户数/人数；记录调查对象和时点，不能把街道人口作为某栋受益人口 |
| 判断依赖 | `affected_dimensions`、`prerequisite_task_ids`；定位到受影响维度及可执行调查任务，不自动改变评分或行动建议 |

每个金额、数量及受益数值用 `value_basis` 分别标记 `fact`（有可回读资料并经核实）、`estimate`（有方法的估算）、`assumption`（方案输入）或 `missing`（缺失）。数字填入后仍标记为 `missing` 是待整理状态，不能拿它参与完整计算。措施是否纳入也保留其依据：用户选择可记为 `assumption`，批准方案中的实际范围经核实才记为 `fact`。

`tax_basis` 可填 `inclusive`、`exclusive`、`not_applicable` 或 `null`。税率未知不能默认免税；含税价不得再次加税。全部单价先统一到相同币种、金额单位及含税口径；缺少转换依据时分别列示，不计算合并总额。`other_costs` 用于不在措施单价中的费用，明确是否计入；设计、监理等不能在工程单价和其他费用中重复计入。未计费用保存在 `excluded_costs` 并说明原因。

`affected_dimensions` 复用现有维度键：`demand` 居民需求、`supply` 公共服务、`adaptation` 居住工程、`implementation` 实施协同、`operations` 长效维护、`resources` 资金交付。它是依赖标记，不是新的评判规则。

## 3. 出资与维护安排

一项出资渠道填写一行 `funding`，用 `funding_id` 防止跨方案重复，填写出资主体和可覆盖措施。`payer_type` 可填 `government`、`utility`、`resident`、`enterprise`、`other` 或留空；主体类型不能证明其已经承担责任。

| 资金记录 | 应如何填写与使用 |
|---|---|
| `planned_amount` | 拟安排金额；可以是方案假设。参与“计划情景缺口”计算 |
| `applied_amount` | 已申请金额；记录申请原文及时间，不能当作获批 |
| `approved_amount` | 批准文件金额；核对对象、用途、有效期和附带条件 |
| `committed_amount` | 各方承诺金额；核对承诺的主体、约束和履行条件，不能直接等同到账 |
| `disbursed_amount` | 截至 `as_of` 累计已拨付金额，注明是否可用于本方案 |
| `spent_amount` | 截至同一时点累计已支出金额；不能又计为可支付余额 |
| `availability_for_this_plan` | 由复核人依据适用规则确定可计入的金额、证据与状态。未复核为 `unknown`；经过复核可记 `reviewed` 或 `not_available` |

`funding_stage` 可填 `planned`、`applied`、`approved`、`committed`、`partially_disbursed`、`disbursed`、`withdrawn`、`unknown`。阶段名称与各金额应有一致证据。同一来源不同阶段金额是过程记录，不能把计划、批准、拨付三列相加。部分拨付也不能把全部批准金额写成到账。`conditions` 保存用途限制、分摊条件及支付节点。

维护按设施或措施填写 `maintenance`：谁接收、谁运行、谁支付，维护责任、服务标准、责任期间、费用期间及收入权限。`responsibility_status` 可填 `unknown`、`proposed`、`agreed`；需要用合同、移交文件或协商记录支持 `agreed`。用户编写的维护安排只能是方案假设。周期不同的费用先列示，得到明确换算条件后才能折算年度金额；一次性投入和年度费用分开展示。

维护收入填写时同时记录 `revenue_rights_basis`。没有经营权或收费依据时收入保持未知，不将预期公共收益写成事实。居民分摊若有明确方案，可作为居民出资行记录；没有受益分组和分摊约定时，不用总投入除户数宣称居民应缴金额。

## 4. 原文依据与待核事项

原文登记在 `evidence`，复用现有 `source_id` 和（上传文档时的）`document_id`、`version`、`locator`。`hash` 对应已有正文哈希，`raw_hash` 对应原始内容哈希，按现有工件实际值填写；没有值就留空，不能以标题、URL 或手写编号冒充内容哈希。`quote` 应能在指定版本与定位处回读，`observed_at` 记录事实适用时点。模板不保存原材料副本，也不新增解析器。

各行的 `field_evidence` 用以下结构关联一条或多条依据：

```json
[{ "fields": ["quantity", "unit_price"], "evidence_refs": ["EVID-实际编号"] }]
```

一条资料只支持工程量时，不能顺带支持单价。证据登记的 `review_status` 为 `unreviewed`、`reviewed` 或 `conflict`；存在哈希和原文不等于已完成业务复核。不同对象、时点、版本或统计口径的数据应分别登记，不自行覆盖成一个“最新值”。方案假设可没有原文，但要说明输入者、原因和待验证条件。

每项任务填写 `missing_fields`、具体问题、责任方、预期材料、对象和措施、受影响维度、补齐后重算的输出。任务状态沿用既有 `suggested/requested`（建议调查/已请求调查）；不能只改状态就宣布资料已经核实。例如，`items[MEASURE-ID].quantity` 指向具体设施的工程量清单，`funding[FUND-ID].availability_for_this_plan` 指向资金批复及本方案可用范围，不写成泛化“完善资料”。

## 5. 静态计算与缺项传播

以下是后续程序实现的计算口径，模板本身不执行公式。计算要记录 `formula_version`、`input_plan_version`、缺项路径和未计费用；基础、完善、提升属于业务分类，不能抵消安全等独立条件。

| 输出 | 公式及缺项处理 |
|---|---|
| 措施投入 `Cᵢ` | 对 `included=true` 的措施，工程量 × 统一口径单价；不含税价在税率已知时转换。`included=false` 贡献 0 并保留明确排除原因；`included=null` 或已纳入但关键值缺失时，该项不可计算 |
| 分类合计 | 同类已纳入措施投入求和；该类有未决定措施或缺项时，完整合计为 `null`。可以另列已知小计及缺失项，不能把小计标为完整预算 |
| 投入合计 | 基础 + 完善 + 提升 + 已纳入的其他费用。预备费按明确的费用基数 × 比例计算；基数、比例或相关费用未定，则预备费和总投入为 `null` |
| 计划情景缺口 | `max(0, 总投入 − 去重后的计划出资合计)`；需要同一对象、期间和用途范围。只说明当前方案假设下的缺口 |
| 未落实资金缺口 | `max(0, 总投入 − 经复核可用于本方案的出资合计)`；只计入 `availability_for_this_plan.status=reviewed` 且金额、证据、规则齐备的部分。已复核为 `not_available` 的渠道贡献 0 并保留依据；任何渠道仍为 `unknown` 时，完整合计和缺口为 `null`，同时列出已核实部分 |
| 户均投入 | 总投入 ÷ 同口径现状户数；分母未知或为 0 则 `null`。这是投入强度，不是居民缴费额 |
| 运维余额 | 同一期间、范围内具有依据的维护收入 − 维护支出；费用周期、收入权限或金额缺失时为 `null` |
| 方案差额 | B 的完整总投入 − A 的完整总投入；任一方案合计未知，差额为 `null`。已知措施的局部差额可以单列并限定范围 |

工程量、单价、预算和出资金额应为非负有限数；差额及运维余额可以为负。运算使用统一单位，金额展示保留到分，计算过程不对每一步提前取整。预备费没有项目依据时留空，不沿用当前界面的默认比例。

各出资行应按渠道和覆盖范围去重；金额超过总投入时显示缺口为 0，但不自动认定资金已落实、维护已明确或项目应推进。填写计划资金、把金额类型改成 `fact`、填入 `approved` 字样，都不能自动生成 `retrofit.funding_confirmed`。是否满足继续研究条件仍由现有事实与适用规则核查。

受益人数不能简单按措施求和：同一住户可能同时受益于管网、无障碍和服务设施。具有去重名册或清晰不重叠范围时才给总数；否则比较各措施范围或已注明方法的估算，不写虚假的“净增受益户数”。收入、成本和受益数值显示各自的事实、估算或方案假设，完整性不等于真实性。

当前 [`calculateRetrofitPlan`](../packages/retrofit/planning.ts) 只计算基础、完善、提升三项输入合计、预备费、计划资金缺口和户均投入；输入是用户方案假设，不改变事实门。它没有读取本模板的措施、资金阶段、维护和版本记录。未来接入时应保留其现有测试和未知值处理，再适配明确的措施明细与结果，不能用本模板宣称上述细项计算已经上线。

## 6. 对照表与可执行结论

先核对两方案的现状快照、对象、模式、研判时点、测算期、报价基期和价税口径是否可比。不同则填写 `non_comparable_reasons`，不能把差额全归因于方案调整。双方修改工程范围时，范围变化本身作为方案差异记录；若变化来自现状重新认定，应先用同一新现状重新整理两方案。

| 比较项 | 方案 A | 方案 B | 变化与影响 |
|---|---|---|---|
| 措施与对象 | 填措施 ID、纳入状态、楼栋/设施 | 沿用措施 ID 填变更后范围 | 新增、删减、修改或仍未知；说明为何变化 |
| 工程量及投入 | 量、单位、含税投入、依据/假设 | 同口径填写 | 单项和总额差额；缺值保留未知 |
| 受益对象 | 人群、户数/人数、空间范围与方法 | 同口径填写 | 哪些对象新增受益、被排除或仍待调查；避免重复计数 |
| 资金安排 | 出资渠道、阶段、可用条件和金额 | 同渠道对照 | 计划变化、批准变化与实际拨付变化分别说明 |
| 维护责任 | 接收/维护/支付主体，周期和费用 | 变更后的责任与费用 | 哪项新增工作由谁承担，哪些责任尚未达成 |
| 关键任务与判断 | 与措施相连的调查任务及依据 | 保留、新增、解除或改变的任务 | 指明补齐后重算什么；没有重评则判断变化保持未知 |

`comparison.measure_changes` 每条可填写 `measure_id`、`change_type`（`added/removed/modified/undecided`）、`from_included`、`to_included`、`changed_fields`、`local_cost_delta`、`evidence_refs`、`reason`。只有双方纳入状态明确，才认定新增或删减；未知不能当作已删减。`beneficiary_changes` 和 `maintenance_changes` 分别记录对象范围、变更说明及依据，`affected_task_ids` 指向现有待核任务。

比较说明可直接填写下面五句话，不预填结论：

> 方案 B 相比 A，在哪些楼栋或设施新增、删减或修改了什么措施，原因是＿＿。在同一测算口径下，完整投入变化为＿＿；尚未计入的是＿＿。受益范围变化为＿＿，计数依据及重叠处理为＿＿。新增或改变的维护责任由＿＿承担，周期及费用依据为＿＿。因此先核实＿＿，取得＿＿后重算＿＿；行动建议是否改变，依据是＿＿。

没有执行新一轮事实与规则判断时，`action_advice_changed` 保持 `null`。模板中的金额、差额和依赖关系能帮助整理比较问题，但不代替专业工程意见、已审核的资金文件或正式投资决定。

## 7. CSV 使用约定

CSV 是 UTF-8 带 BOM 的措施明细表，一行一项措施，以 `plan_id`、`plan_version` 关联完整 JSON；方案口径、出资、维护、证据登记和比较结果仍填在 JSON 中。`object_refs`、`beneficiary_group_refs`、`affected_dimensions`、`prerequisite_task_ids`、`evidence_refs` 多值以 `;` 分隔，`*_basis` 对应 JSON 的 `value_basis`。证据单元格只填引用 ID，具体支持哪些字段在 JSON 的 `field_evidence` 中列明。CSV 不包含隐式公式，空值不得在电子表格中批量替换成零。
