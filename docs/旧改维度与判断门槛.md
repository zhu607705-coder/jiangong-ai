# 旧改维度与判断门槛

更新：2026-10-06。业务目标是决定是否继续尽调与优先核实什么。本轮集中既有业务定义，修复作用域准入与比较维度错位，没有自行设定新的居民同意比例、设施数量或资金收益门槛。

## 同一份维度定义

`packages/retrofit/policy.ts` 是旧改六维的共同入口，保存名称、问题、原有五档描述、资料类型、必需确认项、否决归属及调查动作。地图条件、项目条件、Qwen问题与新比较矩阵均从此处读取。

| 维度 | 当前继续判断所需确认 | 独立否决归属 |
|---|---|---|
| 居民需求 | 居民需求与异议 | 无预设数值否决 |
| 公共服务 | 公共服务缺口 | 无预设数量否决 |
| 居住工程 | 方案相关工程评审 | 安全、保护要求与当前方案冲突 |
| 实施协同 | 实施范围与居民协同 | 权属或实施权限 |
| 长效维护 | 长效维护安排 | 无预设费用比例否决 |
| 资金交付 | 预算与资金落实 | 不把计划金额直接解释成已落实 |

本方案专业规则复核是独立的第七项确认，不放进六维均分。确认事实必须适用于当前项目、时点和方案；没有规则依据不能由模型填一个达标阈值。

## 程序怎样形成行动

`evaluateRetrofitConditions` 按项目研究截止日准入来源和事实，单次按事实类型建立索引。每项条件输出已确认、未成立、缺失或冲突，保留事实与来源ID；每维另外可显示独立否决。无效来源保存拒绝原因与定位，避免把“未适用于项目”混成“现实不存在”。

行动顺序沿用原产品口径：

1. 存在有效、未冲突的独立否决，当前方案暂缓；其他维度的好条件不能抵消。
2. 未发现这种否决，但确认项未成立、缺失、冲突或专业规则未确认，先补充关键资料。
3. 七项确认均成立，建议进一步尽调。它不是施工安全、资金已拨付或投资审批结论。

源文缺失时不写零分；一个否决有冲突时不认作已解除，保留核查；另一项独立否决仍有效。来源版本有哈希只能说明版本有记录，不能代替适用范围。

本轮修复：`scope_kind=shared`且只适用其他楼栋的事实，即使误填当前项目 `object_ref`，也不能满足项目门槛。明确区域/背景来源、其他对象来源同样拒绝；未声明新范围字段的历史事实继续按原精确绑定规则处理。规则版本为 `neighborhood-action-v2`，地图来源签名和 live 工件依赖包含该版本，避免把旧判断当作当前规则结果。

## 比较与界面

新比较矩阵使用 `neighborhood-comparison-v1`：必须完整包含六个维度，并逐维覆盖所有实际候选，不能靠几行相同套话补齐。公共服务与长效维护独立呈现，不再混在组织/企业比较里。契约保留旧维度和值；无版本的历史比较保留原口径，不自动换标签。

项目页新增“条件与行动门槛”，显示各维状态、依据及拒绝原因、独立专业规则确认和研究截止日。雷达仍表示方案适配描述，与条件状态、资料覆盖和行动建议分别展示。

## 模型信号与专业数值门槛

`packages/decision/thresholds.ts` 单独登记现有工程默认值：雷达显示最低置信度0.65；研究分流最低置信度0.8、选项概率0.65、充分性0.75；一般片区标色的适配低档上限2和高档下限3.5。这些值未改变，也不是居民需求、同意率或资金能力的专业达标线。

以后增加数值业务门槛，应先确定指标及单位、分子分母、对象和时点、适用开发模式、规则出处及专业复核版本，再实现对应公式与比较操作。当前资料没有这些已确认数值规则，因此不会由程序拍定“多少人/多少设施/多少利润即可推进”。

验证记录见 `../research/test_results/condition-policy.json`。本机翠苑历史项目按其2026-10-02时点显示六维依据缺失与专业规则未确认，保持补充资料，不因历史投资计划或模型评分推进。本轮没有新增模型调用。
